# Тезисы

1. Качество программы - наша цель.
2. Тесты несовершенны. Иногда недостаточны, а иногда избыточны.
3. Типы в некоторых случаях позволяют обойтись без тестов.
4. Формулировки требований сильно влияют на выбор тесты/типы (сейчас bias в сторону тестов).

Иначе говоря,

    Как писать программы, 
    чтобы гарантировать, что они будут работать правильно, 
    но при этом писать поменьше тестов?

# Качество программ (1)

<b>Качественная программа</b> — (1)
<b>достигает</b> (2) <b>требуемого результата</b> (3) с соблюдением заданных <b>ограничений</b> и (4)
<b>минимизирует</b> <b>целевую функцию</b>.

Где здесь тесты? Где здесь типы?

# Типы (3)

0. Компилятор, статическая система типов.
1. Дженерики и тайп-классы (параметрический полиморфизм).
2. ADT - Алгебраические типы данных.
3. Явный Null (как в Kotlin'е).
4. newtype'ы, Refined-типы, литералы (синглетонные типы).
5. `*` Квитанции эффектов (`newtype Unit`).

# Типы (3.0): компилятор (vs интерпретаторы с динамической типизацией)

Типы:

* каждая строка кода проходит компиляцию
* опечатки
* неправильные аргументы функций
* несовместимые типы в одном выражении

Тесты, которые не нужны:

* 100% покрытие не требуется
* проверка входных данных на соответствие Int/Double
* проверка списка аргументов функции

# Типы (3.1): Дженерики и тайп-классы

Типы:

* некоторые функции определены типами:

```scala
def f[A](a: A): A = ???
val f: [A] => A => A = ???

val identity: [A] => A => A = [A] => (a: A) => a
```

* универсальные функции `map`, `flatMap`, `foldLeft`, `traverse`, ... - написаны один раз, используются многократно;
* cats (Functor, Monad, Concurrent, ...)

Тесты, которые не нужны:

* для каждого типа данных
* обработка ошибок в цепочках вычислений (рельсовое программирование)
* меньше кода — меньше тестов

# Типы (3.2): АДТ (алгебраические типы данных)

Типы:

* точная передача семантики (bool -> enum)
* закрытый список вариантов (enum'ы, sum-типы)
* Either[Error, A] вместо исключений

Тесты?

* тесты исключений (тесты обработки ошибок);
* тесты ветвлений.

Ошибки, не поддающиеся тестированию

* расширение enum при рефакторинге;
* непредусмотренная обработка каких-либо случаев

# Типы (3.3): Явный Null

Типы:

```scala
val x: String | Null = null // ok
-Yexplicit-nulls
```
            
Тесты?

* проверка на null всех N функций и всех комбинаций M аргументов O(N*2^M)

```scala
def foo(a: A|Null, b: B|Null): Int = (a, b) match
  case (null, null) => 0
  case (null,    _) => 1
  case (   _, null) => 2
  case _            => 3
def bar(a: A, b: B): Int = 3
```

# Типы (3.4): newtype'ы, литералы, refined

Типы:

```scala
opaque type Surname <: String = String
opaque type Name <: String = String

case class Success(success: true, 
  port: Int Refined Interval.Closed[49152, 65535])
case class Person(name: Name, surname: Surname)
```

Тесты, которые не нужны:

* Тесты для значений, которые не удовлетворяют предикату.

Ошибки, не поддающиеся тестированию

* Перепутанные однотипные аргументы.

# Типы (3.5): * Квитанции эффектов (доказательства)

(Малоизвестный приём доказательства выполнения эффекта.)

## Доказательство сохранения в БД

```scala
object Db:
  opaque type Identifier[A] = DbGeneratedId

  def create[F[_]: Storage, A](a: A): F[Identifier[A]] = 
    Storage[F].insertReturningId(a)
      .map(id => id: Identifier[A])

object TaskService:
  opaque type TaskId = Identifier[Task]

  def createTask[...](taskDefinition: Task): F[TaskId] = 
    Db.create(taskDefinition)

```

# Типы как теоремы (3) Изоморфизм Карри-Говарда

Основой доказательств является связь между типизированной программой и обычной логикой.

```scala
type Id = [A] => A => A
val identity: Id = a => a

// Modus Ponens
// ∀A, B (A -> B) & A -> B
def modusPonens[A, B](f: A => B, a: A): B = f(a)
val modusPonens: [A] => [B] => ((A => B), A) => B = { 
  case (f, a) => f(a)
}

```

# Какие теоремы интересны в прикладных приложениях? (4)

(Суха, мой друг, теория...)

1. Работоспособность (компилируется == работает).
2. Универсальность (работает для всех входных данных, тотальность).
3. Семантическая корректность (выдает правильный результат).
4. Безопасность (роли, права доступа, аутентификация, авторизация).
5. Побочные эффекты (во внешние системы отправляются уведомления, в БД сохраняются данные, логируется то, что нужно).
6. Бизнес-логика как параметр (основная структура программы не зависит от бизнес-логики).


Бизнес-теоремы отличаются от алгоритмических/математических теорем!

# Формулировка требований (4)

Сравним два требования:

## Требование 1:

> Я, как пользователь, при нажатии на кнопку "Сохранить", должен получить сообщение "Сохранено успешно".

## Требование 2:

> При всех возможных входных данных, если программа завершилась успехом, то гарантируется, что (1) новые данные сохранены в БД; (2) отправлены обязательные уведомления во внешние системы. 
> Если программа завершалась неудачей, то гарантируется, что (1) состояние БД не изменилось; (2)  во внешние системы отправлены компенсирующие уведомления. 

# Заключение (4)

Типы:

1. Явно описанные универсальные требования можно гарантировать только с помощью типов. Тесты не обеспечивают полноты.
2. Интеграцию с внешними системами (на Scala) можно проверить с помощью типов, если использовать общую библиотеку интерфейсов.
3. Интеграцию с внешними системами (не на Scala) можно проверять "почти типами" - с помощью OpenAPI-спецификации, правда, многие семантические особенности отразить невозможно.

Тесты:

1. Некоторые частные ad-hoc требования остаётся проверять только тестами. Типы в таких случаях приводят к чрезмерному усложнению кода.
2. Типы ограничены и не могут представить все нюансы. Поэтому часть требований можно выборочно проверить только тестами.
