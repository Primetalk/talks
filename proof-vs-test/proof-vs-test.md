# Тезисы

1. Качество программы - наша цель.
2. Тесты несовершенны. Иногда недостаточны, а иногда избыточны.
3. Типы в некоторых случаях позволяют обойтись без тестов.
4. Формулировки требований сильно влияют на выбор тесты/типы (сейчас bias в сторону тестов).

Иначе говоря,

    Как писать программы, 
    чтобы гарантировать, что они будут работать правильно, 
    но при этом писать поменьше тестов?

# Типы (3.1): компилятор (vs интерпретаторы с динамической типизацией)

Типы:

* каждая строка кода проходит компиляцию
* опечатки
* неправильные аргументы функций
* несовместимые типы в одном выражении

Тесты, которые не нужны:

* 100% покрытие не требуется
* проверка входных данных на соответствие Int/Double
* проверка списка аргументов функции

# Типы (3.3): Дженерики

Типы:

* некоторые функции определены типами:

```scala
def f[A](a: A): A = ???
val f: [A] => A => A = ???

val identity: [A] => A => A = [A] => (a: A) => a
```

* универсальные функции `map`, `flatMap`, `foldLeft`, `traverse`, ... - написаны один раз, используются многократно

Тесты, которые не нужны:

* для каждого типа данных
* меньше кода — меньше тестов

# Типы (3.4): АДТ (алгебраические типы данных)

Типы:

* точная передача семантики (bool -> enum)
* закрытый список вариантов (enum'ы, sum-типы)
* Either[Error, A] вместо исключений

Тесты?

* тесты исключений (тесты обработки ошибок)
* тесты ветвлений

Не тестируемые проблемы

* расширение enum при рефакторинге
* непредусмотренная обработка каких-либо случаев

# Типы (3.5): Явный Null

Типы:

```scala
              val x: String | Null = null // ok
              -Yexplicit-nulls
```
            
Тесты?

* проверка на null всех N функций и всех комбинаций M аргументов O(N*2^M)

```scala
def foo(a: A|Null, b: B|Null): Int = (a, b) match
  case (null, null) => 0
  case (null,    _) => 1
  case (   _, null) => 2
  case _            => 3
def bar(a: A, b: B): Int = 3
```

# Типы как теоремы (3) Изоморфизм Карри-Говарда

Основой доказательств является связь между типизированной программой и обычной логикой.

```scala
type Id = [A] => A => A
val identity: Id = a => a

// Modus Ponens
// ∀A, B (A -> B) & A -> B
def modusPonens[A, B](f: A => B, a: A): B = f(a)
val modusPonens: [A] => [B] => ((A => B), A) => B = { 
  case (f, a) => f(a)
}

```

# Какие теоремы интересны в прикладных приложениях? (4)

(Суха, мой друг, теория...)

1. Работоспособность (компилируется == работает).
2. Универсальность (работает для всех входных данных, тотальность).
3. Семантическая корректность (выдает правильный результат).
4. Безопасность (роли, права доступа, аутентификация, авторизация).
5. Побочные эффекты (во внешние системы отправляются уведомления, в БД сохраняются данные, логируется то, что нужно).
6. Бизнес-логика как параметр (основная структура программы не зависит от бизнес-логики).


Бизнесовые теоремы отличаются от алгоритмических/математических теорем!!!

# Формулировка требований (4)

Сравним два требования:

## Требование 1:

> Я, как пользователь, при нажатии на кнопку "Сохранить", должен получить сообщение "Сохранено успешно".

## Требование 2:

> При всех возможных входных данных, если программа завершилась успехом, то гарантируется, что (1) новые данные сохранены в БД; (2) отправлены обязательные уведомления во внешние системы. Если программа завершалась неудачей, то гарантируется, что (1) состояние БД не изменилось; (2)  во внешние системы отправлены компенсирующие уведомления.
